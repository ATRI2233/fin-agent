## P0 — 实际 BUG（应立即修复）

### 1. CORS 配置不合法

**文件：** `src/server/app.ts:35-37`

```ts
app.register(cors, {
  origin: "*",
  credentials: true,
})
```

根据 CORS 规范，`Access-Control-Allow-Origin: *` 不允许与 `Access-Control-Allow-Credentials: true` 同时出现，浏览器会拒绝该响应。应改为明确指定 origin 白名单或动态校验。

### 2. Agent 路由吞掉错误类型

**文件：** `src/server/api/v1/routes/agents.ts:24`

```ts
catch {
  throw new ValidationError("Invalid message request");
}
```

`AgentTimeoutError`（应返回 504）和 `AgentHttp5xxError`（应返回 502）被 catch 统一包装成 `ValidationError`（422），客户端永远收不到正确的 HTTP 状态码。

### 3. Conversation 路由用错错误码

**文件：** `src/server/api/v1/routes/conversations.ts:22,52`

```ts
throw new WorkflowNotFoundError(conversationId);
```

conversation 不存在时报 `WorkflowNotFoundError(ErrorCode.1001)`，语义完全错误。应使用 Conversation 相关的错误类。

### 4. MCP 工具调用传错参数

**文件：** `src/server/api/v1/routes/mcp.ts:75`

```ts
dispatcher.dispatch(toolName, args, traceId);
```

将 MCP 工具名作为 agent name 传给 dispatcher。MCP 工具和 agent 是不同的概念，此调用架构上不正确。

### 5. React Router 路由语法无效

**文件：** `src/webui/src/App.tsx:374`

```tsx
<Route path="/workflows/:executionId?" element={<WorkflowMonitor />} />
```

React Router v6 不支持可选路径参数（`?` 后缀）。应拆分为两个路由或使用验证匹配。

### 6. Python MCP Server 异常被广泛静默

**文件：** `src/agents/mcp/` 多个文件

```python
except Exception: return None
except Exception: pass
except Exception as e: return {"error": str(e)}
```

网络故障、API 变动等全被吞掉，生产环境诊断困难。涉及 `ashare`、`cn-macro`、`risk`、`sec-edgar` 四个模块，至少 20+ 处。

## P2 — 过度抽象 / 不必要的复杂度

### TypeScript 后端

#### DI 容器（Registry）被半数模块绕过

**文件：** `src/server/infra/registry.ts` + 路由层

Registry 实现了 IoC 容器，但路由层直接 import 模块级单例（`ConversationRepo`、`WorkflowRepo`、`ExecutionRepo`），只有 `WorkflowRunner` 和 `AgentDispatcher` 通过 Registry 解析。DI 的意义被削弱。

#### 无测试的工厂模式

**文件：** `src/server/modules/{workflow,conversation,execution}/repo.ts`

三个 `create*Repo(db)` 工厂函数均有且只有一个调用点，且无任何测试用不同 db 实例调用。

#### 中间错误类无行为差异

**文件：** `src/server/infra/errors.ts:72-143`

`BizError`、`SystemError`、`InfraError` 三个中间层的构造函数完全相同，纯为分类命名，无行为差异，只增加了分类复杂度。

### Python MCP Server

#### MCP 协议层重复

三个 Server（ashare、cn-macro、risk）各自手写同一套 JSON-RPC 协议处理（initialize、tools/list、tools/call 分发）。sec-edgar 用了 FastMCP 框架，多了一种风格。应将共享协议逻辑抽为基础库。

### React 前端

#### useOpencode.ts 中的重复 Hook 模式

**文件：** `src/webui/src/hooks/useOpencode.ts`（497 行）

约 20 个 mutation hook 遵循完全相同的模式：`method + path + invalidate opencodeKeys.all + onError message.error`，可抽象为统一工厂函数。

#### 两套数据获取系统并存

**文件：** `src/webui/src/hooks/useFetch.ts` vs `@tanstack/react-query`

- `useFetch.ts` + `useMutation.ts` — 自定义的 loading/error/data 管理
- `useExecutions.ts`、`useMcp.ts`、`useOpencode.ts` — 使用 `@tanstack/react-query`

前者缺乏缓存、去重、staleTime，但被部分早期页面使用，造成不一致。

## P4 — 架构 / 设计不一致

### 跨模块耦合

**文件：** `src/server/modules/workflow/service/workflow_runner.ts:3`

直接 import `../../execution/repo.js`（另一个 module 的仓库实现层），绕过模块边界。应通过接口或 service 层隔离。

### Repo 层职责过重

**文件：** `src/server/modules/execution/repo.ts`

既做 DB CRUD，又做 graph traversal BFS（`markDownstreamSkipped`），违反单一职责原则。图遍历逻辑应移至 domain 层。

### 设计范式不一致

**文件：** `src/server/modules/*/repo.ts`  vs  `service/*.ts`

- Repo 层使用工厂函数返回对象字面量（`createExecutionRepo()` => `{ createExecution, ... }`）
- Service 层使用 ES6 class（`WorkflowRunner`、`AgentDispatcher`）

函数式 vs 面向对象混用，增加认知负担。

### Store 过度使用

**文件：** `src/webui/src/store/useUiStore.ts`

`currentRoute` 被持久化到 localStorage，但当前路由已经由 `react-router-dom` 的 `useLocation()` 追踪。双数据源。

### 每个工具类创建独立 Client

**文件：** `src/agents/mcp/sec-edgar/.../tools/base.py`

4 个工具实例各创建一个独立的 `EdgarClient`（含独立的 `TickerCache`），应共享为单例。

### 无缓存策略

**文件：** `src/agents/mcp/ashare/`、`cn-macro/`、`risk/`

三个模块完全没有缓存机制，每个请求直接访问外部 API。仅 sec-edgar 有 TickerCache。

### 空目录骨架

**文件：** `src/server/modules/agent/adapter/`、`src/server/modules/mcp/`、`src/server/modules/workflow/executor/`

三个空目录，Python 架构迁移留下的骨架，TS 侧尚未填充。
